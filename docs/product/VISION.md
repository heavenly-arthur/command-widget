# Видение развития Command Widget

## Продуктовая идея

Command Widget должен стать персональной оперативной памятью инженера: открыть поверх рабочего окна, быстро найти проверенную команду, понять последствия, подставить значения и скопировать результат. Его ценность — скорость, доверие к содержимому и полная автономность, а не количество функций.

Неизменные границы: один владелец, один Mac, офлайн-runtime, отсутствие AI, телеметрии, аккаунтов, облака и глобальных горячих клавиш.

## Рекомендуемая последовательность

### 1. Надёжная личная база — следующий этап

- Завершить добавление, редактирование и безопасное удаление записей.
- Добавить автоматическую локальную резервную копию перед изменением схемы.
- Сделать импорт и экспорт JSON для ручного переноса и восстановления.
- Разделить встроенные и пользовательские записи визуально.

Это мой рекомендуемый следующий выбор: без надёжного CRUD и восстановления дальнейшее наполнение остаётся менее полезным лично для владельца.

### 2. Качественная инженерная шпаргалка

- Добавить уровень риска: безопасно, изменяет состояние, потенциально разрушительно.
- Добавить prerequisites: нужный context, namespace, права, plugin или установленный binary.
- Разбить большие категории на темы: диагностика, workload, сеть, storage, security, state, releases.
- Поддержать несколько примеров и блок «проверить перед запуском».
- Показывать версию инструмента, для которой запись проверена.

### 3. Быстрее ежедневной памяти

- Избранное и «недавно скопированные».
- Навигация с обычной клавиатуры внутри открытого окна.
- Шаблоны параметров: приложение находит `<namespace>`, `<pod>` и другие placeholders, предлагает заполнить их и копирует готовую команду.
- Компактный режим панели и настройка прозрачности/размера.
- Возможность скрывать ненужные встроенные записи и категории.

### 4. Контроль и переносимость данных

- Экспорт/импорт YAML дополнительно к JSON.
- Просмотр diff перед импортом.
- История последних локальных изменений и восстановление записи.
- Команда «проверить целостность базы» с понятным отчётом.

### 5. Версионирование приложения

- Семантические версии приложения и каталога.
- `CHANGELOG.md`, Git tags и локально подписанные GitHub Releases.
- Отображение версии в меню и отдельное окно About.
- Воспроизводимый release-скрипт, который собирает `.app`, запускает тесты и создаёт архив.

Runtime приложения останется офлайн; GitHub используется только как хранилище исходников и релизов.

## Варианты следующего решения

### A — Личная база данных (рекомендую)

CRUD, backup, JSON import/export и восстановление после ошибки. Максимальная практическая ценность и защита пользовательских данных.

### B — Глубина знаний

Риски, prerequisites, тематические группы, версии инструментов и дальнейшее параллельное наполнение шести category-файлов.

### C — Скорость использования

Избранное, история копирования, заполнение placeholders и компактный режим.

### D — Релизный контур

Версия в приложении, changelog, теги, release-build и GitHub Releases.

Можно выбрать один вариант или комбинацию, например `A → B → C → D`.
